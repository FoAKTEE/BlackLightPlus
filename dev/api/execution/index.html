Execution module

BlackLightPlus.Execution — Module
Execution

Where programs run: devices, the Executor protocol with its threaded and pooled implementations, the CPU/GPU switch, the one kernel, residency of host objects on devices, ray sources, scheduling, the image-block worklist, the exact accumulators and the cascade of the Monte Carlo layers. A program is an isbits-after-Adapt functor called per item as prog(item, i, outs...); every executor gives every item the same result. CUDA methods of the device protocol live in the CUDA extension.

BlackLightPlus.Execution.ChildBuffer — Type
ChildBuffer(T, capacity, layout::MCStreamLayout)

Scattered children of one layer of the layered scattering loop, as a structure of arrays: photons::Vector{T} and their streams rngs::Vector{MCRng}, capacity slots, and count[1], the atomic slot counter of spawn attempts. spawn! takes the next slot from the counter and writes the child and its genealogy stream child_rng(rng, event, layout) if the slot exists; a child beyond the capacity is counted and dropped, and overflow reports how many. Children are therefore stored in arrival order, which is not deterministic; their set is.

Policy (the driver's): a layer whose buffer overflowed is rerun from the same inputs with a buffer of capacity at least count[1] (the rerun spawns the identical children, their streams being genealogy-keyed), so no child is ever lost. Read the children with children (copies, safe to hand to the next layer's program) and reset the buffer with empty!. Inside a pool program each device writes a twin buffer of the same capacity; gather! appends the stored children of every twin and adds the attempt counts. In a program run by foreach_cascade! the buffer is the slot that the cascade fills per chunk and generation: only its element type and its layout are read.

BlackLightPlus.Execution.DevicePool — Type
DevicePool(devices; lanes = 2, chunk = :auto)

Persistent multi-device runtime over devices (device handles or CUDA ordinals): lanes worker tasks per device, spawned once, a shared work queue, and one residency cache per device (resident). chunk is the chunk setting of the executors built on the pool with PoolExecutor(pool): a positive item count, or :auto, sized per run (chunk_for). Every device must be functional (BackendUnavailable otherwise). Run Julia with more threads than devices so the workers of different devices run concurrently. close(pool) stops the workers and releases their buffers; a pool built here is the caller's to close, a pool obtained through PoolExecutor(devices) or resolve belongs to the process registry and is closed at exit.

BlackLightPlus.Execution.ExactBins — Type
ExactBins(bands::Bands; nu_min = 1e8, nu_max = 1e16, n_ebins = 200)

Exact spectral accumulator of escaped superphotons: per (row of bands, frequency bin) the photon count and the integer limbs of Σ w and Σ w E (E in mₑc²). Frequency bin i covers ln ν ∈ lnu_min + [(i − 1), i) dlnu with dlnu = ln(nu_max/nu_min)/n_ebins, ν = E mₑc²/h; a photon outside the grid is dropped. record! adds through atomics on host and device arrays alike, so the bins hold the exact sums whatever the order of arrival; merge! adds bins of the same grid by integer addition; Spectrum rounds them once per cell. Inside a pool program the device twin is a zeroed accumulator gathered back by gather!; with any other Adapt adaptor the arrays are adapted.

InclinationBands(incl_deg, half_width_deg)

BlackLightPlus.Execution.cost_order — Method
cost_order(curve, fov, npix; tile = 16) -> Vector{Int}

Queue order of a full npix × npix frame, longest predicted work first: the pixels grouped in tile × tile image tiles (column-major order inside a tile, which keeps the sampling locality of neighbouring rays), the tiles in descending predicted cost. A ray marches longest near the critical curve, where its orbit count grows as the logarithm of the inverse impact-parameter offset, so a pixel's predicted cost is log(n / (d + 1/4)) with d its distance to curve on a grid of max(1, tile ÷ 4)-pixel cells and n the grid size. Tiles of equal cost keep their index order.

BlackLightPlus.Execution.foreach_cascade! — Method
foreach_cascade!(exec, primary, layer, n, depth; capacity = nothing,
                 chunk = cascade_chunk(exec, n)) -> Int

Run a cascade of at most depth + 1 generations on the executor exec: generation 0 is the program primary over the items 1:n, generation g ≥ 1 the program layer over the children that generation g − 1 spawned. The items are cut into chunks of chunk consecutive items, and one worker runs every generation of a chunk before it takes the next chunk. Both programs are called as prog(item, i) without outputs: the primary's item is its global index, the layer's item its member of the Generation the layer program holds, which the cascade replaces by the chunk's children of the previous generation. A program spawns into the ChildBuffer it holds, a slot whose element type and layout the cascade reads (pass one of capacity 0) and which it replaces by the chunk's child buffer. A primary that holds no ChildBuffer spawns nothing, and only generation 0 runs. Returns the number of children spawned in all generations; the children of generation depth are counted, not tracked.

The programs' ExactBins and ExactScalars receive every addition exactly once; call gather! on them afterwards, as after foreach_item!. Children that overflow a buffer are recovered by running their parents again, after the buffer grows, into zeroed scratch accumulators of the same types, so a rerun neither counts twice nor changes the compiled program. On a PoolExecutor each lane passes the chunk's range to the device without staging, keeps the chunk's children in two lane-resident buffers swapped per generation and reads back only their count; a generation that can spawn records into lane scratch, added into the device's totals once its children fit, and an overflowing generation runs again in full. A device generation starts with capacity child slots (nothing: at least MIN_CHILD_SLOTS, half the chunk). On a ThreadedExecutor worker tasks pull the chunks and run their items in order into the shared totals, with two task-local buffers of capacity slots (nothing: MIN_CHILD_SLOTS) that grow; only an item whose children overflow runs again.

Determinism: the accumulated totals, the set of children and the returned count are bitwise independent of the executor, the chunking, the device count, the lane and the arrival order.

BlackLightPlus.Execution.foreach_item! — Method
foreach_item!(exec, prog, items; outs::Tuple = (), order = nothing) -> outs
foreach_item!(exec, (prog1 => items1, prog2 => items2, ...); outs::Tuple = ()) -> outs

Run the program prog once for every item of items (distinct integers) on the executor exec, as prog(item, i, outs...): the program writes its outputs for item at outs[k][i] and returns nothing. i is the slot that the executor gathers into outs[k][item] (the item itself under ThreadedExecutor, the position in the chunk on a device), so after the call outs[k][item] holds the item's outputs. A program without outputs (outs = ()) may write through atomics. order, a permutation of 1:length(items), sets the visiting order to items[order]. The second form queues several programs over their own items in one queue, part by part, sharing outs.

Determinism: bitwise per item, whatever the executor, chunk size, device count, lane scheduling or order.

BlackLightPlus.Execution.stream_blocks! — Method
stream_blocks!(exec, prog, work, block, visit; outtype = Float64)

Run the refinement worklist: march every ImageBlock of work and of the children that visits return, until none remain. A chunk of blocks (at most max(1, c ÷ block²) of them, c the executor's chunk for the pixels of work, resolve_chunk!) is one run of the program prog over the chunk's block × block pixels, prog seeing its BlockGrid filled with the chunk's blocks (so prog must reach that grid through Adapt.adapt_structure). Each item writes one value of type outtype. Then visit(blk, vals) is called for each block of the chunk, vals[(i - 1) * block + j] holding pixel (i, j) at (a0 + (i - 0.5) ps, b0 + (j - 0.5) ps), ps = span / block; it returns the block's children (any iterable of ImageBlock), which are queued at once. visit may run concurrently for different blocks, may keep vals, and must not start executor work.

Determinism: the visited blocks and each block's values are bitwise independent of the executor, the chunking, the device count and the completion order.

BlackLightPlus.Execution.chunk_for — Method
chunk_for(exec, n; hint = nothing, bytes = 0) -> Int

The chunk of a run of n items on exec whose program writes bytes of outputs per item and has the chunk_hint hint: the executor's chunk setting when it is an integer, else the rule of :auto:

  • a pool on one device: 2^20, one launch per run of up to 2^20 items;
  • a pool on d > 1 devices of l lanes: clamp(cld(n, 2 l d), 2^16, 2^20), two chunks per lane where the run is large enough;
  • on a pool, at most max(2^16, 2^24 ÷ bytes), so that the outputs of one launch (at most 16 MiB), copied back and scattered by its lane, overlap the launches of the others;
  • threads: clamp(cld(n, 16 t), 16, 4096) on t Julia threads;

then at most hint. Results never depend on the chunk.
