GPU execution

How BlackLightPlus runs its programs on Julia threads and on GPUs: which schedule each executor uses, the primitives and buffers of the device schedule of the Monte Carlo photon phase, the invariants that keep every result bitwise independent of the schedule and why they hold, how a program is added, and how execution is measured. The program contract, the pool and the residency protocol are specified in Architecture §4.2; the knobs and the records of measured speed are in Performance.

Status. Normative. A component marked gated is part of the standard while its gate in §9 holds; without it the component is absent and the form named in the last column of its §9 row serves its programs. §9 gives each gate's measurement; a component whose gate failed is not built, and §10 gives the reason. The records are in results/blp/gpu_infra/: the plan with its gates and targets, and RECORD.md, every component's outcome and the final verification of the tree 12bc068, bitwise the references of f6decd6 on every deck and backend.

1. The measurements the design rests on

Nsight Compute and Nsight Systems on the history schedule of §3, and a probe that stamps every photon's steps, events, start, end and SM.

2. Execution model

2.1 One kernel, programs, executors

There is one kernel, _foreach!, one thread per item, no shared memory and no barrier. Every device algorithm, the queues, the counting sort, the counter resets and the drains included, is a program run by _foreach! or a device-protocol function whose CUDA method lives in the extension. A program is an isbits-after-Adapt functor called as prog(item, i, outs...) (Architecture §4.2).

The programs of a run over an emission window (TimedPrimary, TimedLayer, TimedRecord) are host programs: mc_spectrum with a window runs only on a ThreadedExecutor.

The schedule is a property of the device and of the programs: foreach_wavefront! runs the wavefront when every device of the pool answers wavefront(dev) = true (a CUDADevice; the test device Decks.WaveHost also answers true), the settings allow it and the Wavefront carries stage programs for the call (any call without children; a call with children when it has a branch stage), and calls foreach_cascade! with its history programs otherwise; on a device that cascade takes the device-budget child slots of §3. The CPU or GPU is chosen only by the one backend option (keyword, then the session default, then BLP_BACKEND, then :auto); no plan, configuration, product keyword or function name names a backend.

The budget, cohort, refill, doubling, sort, launch, block-order and workgroup settings of §4.3 are constants of the Execution layer. Tests and benchmarks change them only inside with_wavefront_settings(f; budget, cohort, refill, doubling, wavefront, sort_every, wait, cost_order, workgroup), a scoped value that the driver reads on the host (wavefront = false runs the cascade of the same programs, for comparison); outside that scope every call uses the defaults. describe(exec) reports, for the executor's last Monte Carlo call, its schedule (:cascade or :wavefront), the settings used (with the budget and the cohort the call started from), the primaries admitted, the children spawned and the wavefront iterations of each device, and the reruns; wave_log(exec) returns each device's per-iteration records (live states, budget, counts, reruns, whether the cohort was sorted, and the host seconds of each stage).

Threads keep the history schedule because a CPU thread runs one photon at a time: there are no SIMT lanes for a segment to recover, and the host's floating-point contraction depends on the inlining context, so the fused track! is both the fast and the bit-stable form on the host.

2.3 Lanes and shared twins (gated)

A device runs two lanes, each a task with its own stream. Their launches overlap when no array of one launch waits on the other lane's stream. CUDA.jl orders a device array by the stream that last converted it to a pointer: the conversion synchronises with the previous owner and makes the converting stream the owner, also with synchronisation disabled, and a pool free, from a finalizer too, is ordered only against the owner. share_lanes!(dev, a) (device protocol; identity on a HostDevice; on a CUDADevice it synchronises the stream that wrote a and calls CUDA.enable_synchronization!(a, false)) exempts an array from the implicit synchronisation. The rule:

  1. Only residency twins are shared: complete after a synchronised upload, never written.
  2. Every device array that a launch writes is lane-owned. Accumulator twins (ExactBins, ExactScalars) and ChildBuffer twins are registered per lane and folded by gather! over the twins of every lane; lane_buffer, lane_array, lane_stage, the cascade's generations and the wavefront's queues are used by one stream.
  3. A shared array lives until every lane of its device has synchronised. A call's program twins hold their residency twins until sync_lanes(pool, dev) at the end of the call; an eviction from the residency cache, and invalidate! of host arrays a caller overwrites (§2.7), synchronise every lane of the device and then free the arrays explicitly; no shared array is left to a finalizer while a lane can use it.
  4. With the lane check on (lane_check!(true), a debug switch, off by default), every gather! of accumulator or child twins, which frees their device arrays without waiting, asserts that the stream of every lane of each twin's device is idle. An eviction is not checked: it waits for every lane before it frees. A lane frees its own buffers while the other lanes run. With sharing off (lane_sharing!(false)), every array uploaded from then on keeps CUDA.jl's synchronisation, the form compared against.

The wavefront uses the first lane of each device (§4.6); the cascade, the imaging and the crossing programs use both.

2.4 Several devices

Lanes of every device pull from one chunk queue (per-item products and the cascade), or every device draws primary blocks from one host-side atomic block counter (the wavefront). Children never leave the device that spawned them. Each device holds its own residency copies and its own accumulator twins, folded into the host sums by exact integer addition. Every device of one architecture runs the same compiled programs, so one GPU and two GPUs give bitwise equal results. A two-GPU Slurm job holds the node's four CPUs, as a one-GPU job does.

2.5 Launch traits

Per program type, each with the default that leaves the backend's choice: workgroupsize (64 for IQUV imaging, 32 for the Monte Carlo history programs MCPrimary and MCLayer, 128 for the wavefront's stage and key programs), chunk_hint, stack_bytes (32 KiB for the exact-Kerr programs) and register_cap (gated, §9: the most registers per thread, honoured by the extension's launch_capped!, which compiles _foreach! with maxregs and otherwise launches as the backend does; 168 for the thin MCPrimary, which runs wherever the thin phase takes the cascade; every other program, the stage programs included, is uncapped). A register cap and a workgroup size reach only ptxas and the launch configuration: the PTX of the program is the same but for the .maxnreg directive of a capped entry.

2.6 Compilation (gated)

The extension's precompile workload (PrecompileTools) compiles one trivial program through _foreach! to a cubin for sm80, in a session with the package, ForwardDiff and CUDA loaded. ForwardDiff's `promoteruleinvalidates the GPU compiler's native code that CUDA's own image holds, so without the workload the first device compilation of a session compiles that code again, 6–7 s whatever the program; with it the code is kept in the extension's image for every session that loads ForwardDiff before CUDA, asusing BlackLightPlus, CUDAdoes. A session that loads CUDA first keeps the 7 s. The device code of every program is compiled in each session: an inferred device code instance does not survive an image load (its edges to KernelAbstractions' device overrides and tosetindex!` on device arrays do not verify), so deck-independent programs in the workload and GPUCompiler's disk cache would keep nothing (§10). The workload changes the package images a session loads, so its gate includes the host bits of the CPU decks in a process with CUDA loaded.

2.7 Host outputs (gated)

A product's host epilogue (the band sums I = ((0 + I₁) + I₂) + …, the NaN maps of the observables a radius-only call skips, the zero planes of a Stokes I image, the split of the IQUV planes) runs as programs (BandSum, Fill, Split) on ThreadedExecutor(chunk = 2^14) over the host arrays, whatever the run's executor. Reductions whose order fixes their bits (the light curve of analytic_movie, the flux of sensitivity, the deposits and the weighted composite of photon_ring_layers, zone_offsets) stay serial on the host.

render, render_crossings, render_analytic and analytic_movie take into, an earlier result of the same shape, and write their maps and epilogues into its arrays; the result is bitwise the one without into. Before the call overwrites them, the device copies of those arrays are dropped from every pool's residency caches (invalidate!), so the next upload copies the new values. With into a call allocates at most 0.31 MiB on the host on every backend; analytic_movie on a pool still uploads its landing maps to every device at every call (4 × K × N × 8 bytes per device for K bands of N pixels).

3. The cascade

foreach_cascade!(exec, primary, layer, n, depth; capacity, chunk) runs the primaries in chunks and, inside each chunk, every scattering generation of their children on the worker that took the chunk (Architecture §4.2). It is the schedule of threads and host pools, of runs over an emission window, of generic cascade programs, and of a device phase that the wavefront does not serve (wavefront = false, or a phase whose gate does not hold). The children of generation depth are counted in the returned total and not tracked.

  • Threads. Each task keeps two growing child buffers and reruns only the item whose children overflowed, into discarded scratch.
  • Lanes. The chunk's children live in two lane buffers swapped per generation; the only host read per generation is their count. A generation that can spawn records into zeroed lane scratch, drained into the lane's totals once its children fit.
  • Child slots. Without an explicit capacity, a chunk of m primaries starts every non-final generation with max(MIN_CHILD_SLOTS, cld(m, 2), learned(dev), min(budget(dev), 16 m)) slots (gated: the last two terms; without them the rule is max(MIN_CHILD_SLOTS, cld(m, 2), carried), carried the slots the lane grew to in its earlier chunks of the call). budget(dev) = free_bytes(dev) ÷ 8 ÷ (2 × lanes × (sizeof(T) + sizeof(MCRng))) (0 on a HostDevice) and learned(dev) is the largest child count any non-final generation on the device has spawned in the process (kept by the pool under its lock); 16 m caps the budget term. On an 80 GB A100 with two lanes the budget is about 1.49 × 10⁷ slots per side and lane; at a chunk of 250,002 primaries the cap 16 m is 4.0 × 10⁶ slots, 672 MB per side, against at most 1.93 × 10⁶ children of a generation of the torus deck. An explicit capacity is the starting slot count of every generation of every chunk, bypassing the rule, the learned slots and the slots carried from earlier generations and chunks, so a small capacity overflows. A generation whose children overflow runs again in full with slots for its counted children and an eighth more; describe counts these reruns. Capacity never changes a bit.

The counter block of the lane holds five Int64: live, done, children, dropped (children beyond the depth, §4.7) and fault (§4.2).

4.2 One iteration on a device

Before the advance the host grows the lane's buffers to the preconditions cap_B ≥ max(nA + cap_C, min(P + R − 1, nA + cap_C + r)) (r the primaries not yet taken) and cap_D ≥ nA: every member yields one state, the branch adds at most cap_C, and the refill stops once P states are live, past P by less than a block. With nA live states in A:

  1. Sort (gated; with a key stage, before every sort_every-th advance of the device, from its first): the counts zeroed by a copy from a pinned stage of zeros; MCKey writes a key per member and counts it by an integer atomic; one copy of the counts to the host, which checks that they sum to nA; an exclusive scan; one copy of the cursors back; KeyPlace writes q[cursor[key]++] = j. Without a sort q is the identity.
  2. Zero the counter block by a one-item program on the lane's stream.
  3. Advance over 1:nA: member j runs march_steps on A[q[j]] up to step last = min(it − 1 + min(K, M), M) (M = max_steps(ctl), computed in Int64) and admits the state to B if it is still live, to D if it stopped; its children go to C through the sink. A survivor whose it did not grow, or a stopped state without an outcome, adds one to fault.
  4. Read the counter block: one copy into a pinned stage, then a synchronisation of the lane's stream; the host reads the stage only after it. Each of fault > 0, live + done ≠ nA, live > cap_B and done > cap_D is an error. If children > cap_C: grow C to children + children ÷ 8 slots (and B with it), count a rerun, and repeat from step 2 on the unchanged A and q.
  5. Retire over 1:nD: march_close, i.e. record! and tally!.
  6. Branch over 1:nC: march_open of every child, admitted to B, or counted into dropped beyond the depth (§4.7); then a second read of the counter block, whose live must equal the survivors plus the children less those dropped.
  7. Refill: when nB < P and primary blocks remain, one claim on the shared counter (§4.3) and one start launch per run of consecutive blocks taken.
  8. Swap A and B. Stop when nA = 0 and no block remains.

At the end of the call each of these is checked, and a failure is an error: the primaries started equal n; the started ranges of all devices partition 1:n; the photons retired equal n plus the children spawned less those dropped. While nA > 0, no retirement in M + 2 consecutive iterations is an error: a state's it grows in every advance and a state stops at it = M, so each retires within M + 1 iterations of its admission.

The advance writes nothing but its queues and the counter block, and its draws come from per-photon streams, so a repeated advance yields the same survivors, retirees and children: an overflow costs one more advance launch, not a generation. With an explicit capacity, cap_C returns to capacity at every iteration; without one, it starts at the larger of P and the child slots the device's first lane holds from earlier calls, and carries every growth across iterations and calls. A call without children (depth = 0) stores no child: the advance counts them, all dropped, and no branch runs. The child count of the call is the sum of the children counters of the advances that succeeded, the number the cascade returns.

Host and stream order. By default no launch waits (WAVE_WAIT = false): the launches and copies of an iteration are queued in the order above on the lane's stream, and the host waits only before it reads the counter block (after the advance and after the branch) and the sort's counts, at most three waits per iteration. The host makes the device forms of the retire and the branch while the advance runs. Three rules make the queued form bitwise the waiting one: the host writes no buffer that a queued copy or launch reads (launch ranges and settings are kernel arguments, the counter block is zeroed by a launch, the sort's zero stage is written only when new); two pinned counter stages alternate by read, so a queued copy never targets the stage the host reads; an overflow rerun zeroes the counter block on the stream before the repeated advance. wait = true makes every launch wait for its device.

The defaults are the best medians of sweeps on the stride-1 timing deck on one A100, every point bitwise: budget 32 runs the thin phase in 0.976 of its time at 16 (five processes of ten calls); budget 16, cohort 2^19 and stage blocks of 128 run the Compton phase in 0.969 of its time at budget 32, cohort 2^18 and blocks of 32 (nine calls in three processes), and budgets of 64 and more or cohorts of 2^17 and less slow it by 7–26 %. Against index order the cost order runs the Compton phase 1.5–1.9 % faster on one A100 and 3.2 % on two; the work per primary of the timing deck peaks at the middle zone radii, not the inner ones, so the gain is measured, not explained.

Children join B in the iteration they are spawned, before any refill, so the cohort grows during a burst of spawning and the refill pauses. Within an advance a photon that stops partway idles for the rest of the launch, about K / (2 L) of its lane-steps for a mean remaining life of L steps (3.5 % for thin photons at K = 32, L = 458). Results do not depend on K, the doubling, P, R, the block order, the sort, the order inside a bucket, whether launches wait, the arrival wait or the workgroup size.

4.4 The scattering stage

The advance calls the sink's branch!(sink, ev, crng) with the ScatterEvent of the step; its default runs kick(ev) and spawn! inside the march exactly as track! does (the inline kick). The child queue holds Superphoton and MCRng (168 B) and MCBranch opens each child (its start sample and rates). The step body is that of track!, kick included, and threads run the same branch!. The event-site sample stays in the march: moving it out would rebuild the parent's per-photon sums out of their step order. A kick in a launch of its own is not part of the standard (§10).

4.5 The coherence sort (gated)

photon_key(st, ctl, y) of a state at x with covariant momentum p on the spacetime st under the march control ctl is (s × 8 + octant(x)) × 8 + octant(k), a total function with values in 0:8191:

  • s, the shell of the coordinate radius r: with r_min = horizon_floor(st) when that is positive and finite, and the march radius of ctl times e^−6.4 otherwise, s = 0 when r is not finite or r ≤ r_min, else unsafe_trunc(Int, min((log r − log r_min) / 0.05, 127.0)), the clamp taken in Float64 before the conversion, the logarithm tang_log;
  • octant(x) the sign bits of the position, octant(k) those of the spatial wave vector k^i = g^{iν} p_ν with the inverse metric of st at x;
  • a state with a non-finite coordinate has key 0.

The key stage MCKey of a Monte Carlo run keys a state by its scattering generation g (the entry photon's nscatt, at most max_scatt) first, then by photon_key: g × 8192 + photon_key, one of (max_scatt + 1) × 8192 values. mc_wavefront gives it to scattering runs only. The sort moves indices, never states, and an overflow rerun keeps the order.

The sort gains by lane efficiency, not memory coherence. On the Compton deck of 1.6 × 10⁵ primaries the advance sorted by generation, then photon_key, runs 24 % fewer warp instructions than unsorted (18.1 against 13.8 active threads per instruction) while loading more sectors per global request (14.6 against 13.4); sorted by photon_key alone it loads the fewest (11.1) and runs 1.2 % shorter. Grouped by generation, the photons of a warp have alike step costs (§1) and run more of each instruction together. The thin march (L1 96 %, DRAM 0.3 % of peak) is not memory-bound and is not sorted.

4.6 Several devices and lanes

Each device runs one wavefront on its first lane; the device's second lane serves the per-item programs and the cascade. Before its first refill a device waits, at most WAVE_ARRIVAL, until every device of the call is ready, so a device whose set-up ends first does not take the blocks of a small call alone. Block claiming ends within one block on every device; the end of the run is each device's own tail of long photons and their children, so two devices do not halve the tail. Children stay on their device. Each stage program has one device twin per device and lane, with zeroed accumulator twins registered on the host accumulators and folded by gather!; the primaries admitted and the children spawned are counted per device.

4.7 What the wavefront serves

  • Wavefront(; start, advance, retire, primary, layer, branch = nothing, key = nothing, doubling_cap = typemax(Int)) holds the stage programs and the history programs of the same transport; the constructor checks that the stage programs agree on the state type (wave_state), that the advance has a positive step limit (wave_steps) and that a key stage has at least one key value (wave_keys). mc_wavefront requires the scattering depth of the run to be the transport's max_scatt, so a Monte Carlo photon of the last generation never spawns (spawning = S && nscatt < max_scatt).
  • A state's generation is generation(state) (for a MarchState, the entry photon's nscatt). A child whose generation would exceed depth is counted in the returned total and dropped, as the cascade counts and does not track the children of generation depth.
  • The start program may predict the cost of each block of primaries (block_costs(prog, n, R), nothing by default), which orders the refill (§4.3).
  • Runs over an emission window run on threads (§2.2); generic cascade programs take the cascade on every executor.
  • foreach_wavefront! returns the number of children spawned, as foreach_cascade!. In finally it empties the child slot of every stage and history program, as the cascade does; the pool job that ran it synchronises the lanes it used.

What follows for each comparison of the protocol (§8.1):

  • CPU, 1 against 16 threads. The threaded cascade's chunks depend on n and the chunk, the totals are exact and an overflow reruns one item: bitwise.
  • CPU against the reference tree. Threads run track! as composed in I13; bitwise is checked on every CPU deck, the window and coverage decks included, in a process without CUDA and in one with CUDA loaded, because host bits follow the inlining context and the package image that compiled a dependency's function, and an equal source is no proof.
  • GPU against the reference tree. The cascade's knobs (slots, overlap, cap, workgroup) change no compiled arithmetic (I14, I15). The wavefront runs the statements of track! split at the back edge (I12) in stage programs (I13); its bits are checked on every Monte Carlo deck at budgets K ∈ {1, 7, 32, ∞} with doubling off, a dependence on K exposing a fusion across the cut, at every launch setting (launches waiting or not, index or cost order, sorted every advance, every fourth or never, workgroups of 64 and 256, cohort 4,096 with refill 64), at child capacity 1, and in the photon records of every generation.
  • One GPU against two. I1–I5, I10: bitwise, checked on decks on which every device admits primaries and, where the deck spawns, spawns children (§4.6).
  • CPU against GPU. The metric depends on the output. Monte Carlo bins: equal counts in every cell, the relative difference of the rounded sums per cell. Monte Carlo scalars and the ledger: equal counts, the relative difference per value. Images and crossings: the largest difference over finite cells divided by the leaf's largest finite magnitude; integer-valued fields (crossing steps, redshift sign) equal. Everywhere the NaN and Inf masks are equal. Per deck the difference is no larger than the reference tree's own CPU–GPU difference under the same metric, recorded with the reference at f6decd6: from 2.2e-16 to 3.1e-10 on the Monte Carlo decks, 8.1e-13 (thin) and 5.5e-10 (Compton) per cell at stride 1, 2.51e-13 and 3.15e-13 on the torus images, 9.03e-11 on the precise march and 2.31e-9 on the closed-form disk.
  • Host pools. A pool of HostDevices runs the cascade with the compiled programs of threads and is bitwise the threads. A WaveHost pool runs the stage programs on the host: bitwise among its device counts, budgets, doubling, cohorts, refills, block orders, sorts and launch forms (one compiled advance, K a runtime argument), and within 1e-11 of threads, whose track! is another inlining context.

Class of a change (decides its verification):

  • A, outside the compiled body: visiting order, chunking, regrouping, compaction, lanes, devices, workgroup size, register allocation, child capacity, where an output lives, when a kernel compiles. Bitwise by I1–I11, I14, I15; the decks confirm it.
  • B, inside the body, exact operation for operation: moving an inlining boundary, splitting a loop, a new enclosing program, a value carried from one step to the next. StaticArrays dot and M*v, muladd and ForwardDiff partials carry reassoc or contract, which LLVM treats by context; bitwise only if the decks on both backends say so.
  • C, through a re-baseline: a change that is known to move bits on a backend (BLP-owned ports of the vendor library's elementary functions on the device; explicit fma reductions on the host). Outside this standard until the reference is re-taken.

7. Adding a program

7.1 A per-item program

  1. A functor whose fields are what the item needs; arrays become device twins by Adapt (inputs uploaded once per device by identity, behind readonly).
  2. prog(item, i, outs...) computes from item alone and writes outs[k][i], or writes through exact accumulators when it has no outputs. No floating-point atomics, no read of i in arithmetic, no partial float sum across items.
  3. Launch traits only when measured: workgroupsize, chunk_hint, stack_bytes, register_cap.
  4. Tests: device_isbits of the device twin, no allocation on the host, bitwise equality of threads, :host_pool and Decks.hosts(1, 2, 3, 5); under BLP_TEST_DEVICES=cuda one and two GPUs bitwise each other.
  5. A case in bench/kernel_audit.jl for its registers, stack and spills, and its entry in the offline device-code screen (§8.3).

7.2 A Monte Carlo transport

  1. The march description March (control, spacetime, provider, opacities, sink, the absorption and scattering switches) and the three @inline pieces march_open, march_steps, march_close over MarchState; track! is their composition.
  2. A sink implementing the Sink protocol (record!, tally!, child_stream, spawn!, branch!), whose child slot is a ChildBuffer of the child element type.
  3. The history programs (MCPrimary, MCLayer or their equivalents): the CPU path and the oracle of the bit tests.
  4. The stage programs built from the same transport and sink (start, advance, retire, and for a scattering run a branch and a key stage), answering wave_state, the advance wave_steps and the key stage wave_keys, a state type answering generation, optionally the start program's block_costs, and the Wavefront that holds both sets.
  5. Streams: a primary's from primary_rng(seed, g), a child's from child_stream with the parent's ordinal nev; no other source of randomness.
  6. Tests: the budget sweep with doubling off on WaveHost pools and on a device, launches waiting and not, sorted and not, at child capacity 1; a run whose march control has a small nmax (the step limit); and the ledger's sums and counts of every quantity.

7.3 Code that must give the same bits in another context

A function whose bits must not depend on where it is inlined, or that must give the host's bits on a device, is written in portable arithmetic: + - * /, sqrt, explicit fma, min, max, abs, copysign, conversions, comparisons, integer arithmetic and BLP-owned ports of elementary functions (tang_exp, tang_log); no muladd, no StaticArrays reduction or product, no ^ with a non-literal exponent, no @fastmath, no call into a non-inlined Base or dependency math specialisation. The zone-table and hot-cross programs are written this way and are bitwise host = device. Converting existing physics to this form moves bits (class C).

8. Measuring

8.1 Bits

  • Reference. A detached worktree at the base commit with its own environment (its BlackLightPlus path is that worktree, never a moving checkout), whose Manifest and LocalPreferences.toml equal the branch environment's but for the change under test. Its CPU decks run in the same session window as the branch's; its device decks on one A100 and on two A100s are recorded once per base.
  • Host-bit fingerprint. Every deck file and job header carries the bits of hypot(56.95171875, -6.4125000000000005), the CPU target of every loaded package image, and the Julia, CUDA runtime and driver versions. A comparison of files whose fingerprints differ is void.
  • Decks. The thirteen fixed decks (Monte Carlo torus thin and Compton at stride 8, thin at stride 1, the thin and the scattering sphere, the marched disks A and B precise and production, the Kerr disk and its radius path, torus Stokes I and IQUV); the coverage decks (a static binary metric, thin and scattering); the ledger decks (run_layers on the torus thin and Compton and on the scattering sphere, with every ledger quantity's sum and count over the stripes and the child count) and the step-limit decks (the curved and the flat march at a small nmax), all on threads and devices; and, on threads only, the window decks (the torus, the scattering sphere, a VariableSphere, a Corotating plasma on the moving binary, a FrameSequence). Every field of every result but the plan and the run record is serialised.
  • Comparison. Leaf by leaf, bitwise or under the metric of §6. A deck missing from either file, a different number of leaves, or a leaf of another shape or element type is a failure; the number of decks and leaves compared is printed and must equal the deck manifest; the exit status is the verdict. The CPU–GPU gap check reads a CPU file and a GPU file of one commit, the HEAD of the tree under test.
  • Two devices. One process runs the device decks on one device and on two, and again at a cohort and refill small enough that every device takes blocks; the run reports two devices, every device admitted primaries and, in every deck that spawns, spawned children.
  • Photon records. For a Monte Carlo deck, every photon's end state (x, p, w, outcome, nev, steps), ledger values and children, keyed by stream identity and sorted, so a difference is located to one photon and one step. They are taken at march_close whatever the schedule, through a forwarding control and sink that forward the whole Sink protocol. On a device the recorded run's bins equal the plain run's; on the host the forwarding types change the inlining context, so host records locate a difference and the decks decide.
  • Stride-1 bins. The thin and Compton photon phases of the timing deck, every cell of every order, every ledger sum and count and the child count, on one device and on two.
  • Repetition. A schedule with shared arrays or launches that do not wait runs each Monte Carlo deck several times in one job; the runs are bitwise each other.

8.2 Time

  • GPU. One Slurm job per comparison on partition preempt (one A100, or two for the two-device rows, -c 4, julia -t 4, JULIA_PKG_OFFLINE=true, the CUDA runtime pinned to 13.3 in LocalPreferences.toml). Processes alternate reference and branch, first and last the reference; each loads the snapshot, builds the sites and tables, compiles each phase once and times its warm calls around run_layers. The thin phase: five processes of ten calls; the statistic is the median of the branch's calls over the median of the reference's, and δ the spread of the reference processes' medians (largest over smallest, less 1, at least 0.01). The Compton phase: three processes of three calls (a cascade call takes 50–66 s), δ the range of the reference calls over their median. Imaging rows: at least three processes, every call kept, with the GC time of each call beside the rows that allocate hundreds of MiB. "Kept" is a statistic at most 1 + δ. Every call's bins, ledger and child count equal the reference's; the SM clock is sampled through the job. A preempted job is rerun whole, never merged. Host-bound rows (the site scan, the zone tables, the full closed-form call) are reported, not gated, by a change that does not edit their code.
  • CPU. 32 threads pinned to 32 physical cores of one NUMA node, at least five interleaved reference–branch pairs, per run the wall time, the per-thread CPU time and the load average. The statistic is the median of the paired ratios with its 90 % interval; the noise half-width δ is that interval's for two identical trees measured the same way. "Kept" is a median ratio at most 1 + δ; "faster by x" is an interval wholly below 1 − x.
  • Ratios. A target is a ratio to the baseline recorded with the reference; the absolute time is information. A three-call comparison resolves the thin phase to about 2 % (the calls of one tree spread over 3.70–4.25 s), and the range of the calls grows with their number (0.137 over 30 calls against 0.004 between three process medians), hence the process medians.

8.3 Profiles and device code

  • Nsight Compute (application clocks, kernel replay, one call between cuProfilerStart and cuProfilerStop on a pool of one lane; --set full, or a limited metric set for a launch longer than a few seconds): smsp__thread_inst_executed_per_inst_executed.ratio (active threads per instruction), smsp__sass_average_branch_targets_threads_uniform.pct, sectors per global load request, L1 and L2 hit rates, local-memory traffic, the FP64 pipe, issue activity, achieved occupancy and the warp stall reasons. The Compton kernels are profiled at Ns = 1.6 × 10⁵: replay costs about 290 times a kernel's duration.
  • Nsight Systems (--trace=cuda,nvtx --gpu-metrics-devices=all --gpu-metrics-frequency=2000): kernel union against the sum (lane overlap), host gaps between launches, SMs active and warps in flight over the call, module-load intervals (compilation).
  • Photon probe. Wrappers of the march control and the sink that record each photon's steps, events, outcome, start and end %globaltimer, %smid and stream identity; the lane efficiency E, residency and warp spans follow from them. On a device the probe's bins equal the plain run's.
  • Offline device code (no GPU): bench/kernel_audit.jl compiles the device twin of every program kind for sm80 and reports registers, stack and spills against its baseline (--check fails on growth). The device-code screen checks, from the PTX that `CUDA.@devicecodedumps: no floating-point operation in a kernel entry; the counts of unroundedmul.f64,add.f64andfma.f64per program (none ofmulandfmain the Monte Carlo programs); per function the counts ofDFMA,DMULandDADDwith their rounding and ofcontractandreassocinstructions, against the reference tree; for capped against uncapped builds, the PTX equal but for.maxnregand theDFMAcount of every function equal, the sequences and theDMULandDADD` counts reported. The screen locates a change; it does not decide bits, which the decks do.

10. Not part of the standard, and why

  • A single persistent loop that regenerates photons, and a claim loop inside the advance. Neither has an exit at which a warp reconverges, and spawning warps measurably do not reconverge at the end of a march; split groups would accumulate over the launch. A warp vote at the loop head would hang on partial warps and cannot be exercised on host pools.
  • A second lane for the longest survivors. A pool job cannot start from inside a pool worker, and two wavefronts on one device double the tail.
  • Per-operation stages and a step split between geodesic and plasma. 2–7.7× slower than a megakernel (Dr.Jit), 72 B of state per step, and a step-internal cut whose bits depend on context.
  • The event-site sample outside the march. It rebuilds the parent's spawned and unspawned sums out of their step order (I7).
  • A kick in a launch of its own (the deferred kick). With the Compton sampler absent and spawn! kept, the Compton primaries still run 15,790 warp instructions per warp-step against 16,702 with it (the gate asked for fewer than 8,000): the sampler is not what splits spawning warps, and a deferred kick would add a 552-byte child record and a launch per iteration.
  • Budget doubling up to M for states that can spawn. The model of the Compton phase puts it at 20.9–28.5 s against 13.5 s with the cap of 128 (estimate).
  • A wavefront on threads. No SIMT lanes to recover; event-based transport is 1.8–4× slower on CPUs; the host's contraction would move bits.
  • Runs over an emission window on devices. The timed programs are host programs (§2.2).
  • Rerunning only the parents whose children overflowed. The wavefront's advance reruns one side-effect-free launch, and the cascade's device-budget slots make an overflow rare.
  • A pilot march that predicts step counts for the order key. A second march control to maintain; the generation and the shell of the key order the photons.
  • A Matter protocol function for the sort key. photon_key from the state, the spacetime and the march control is as coherent by lane efficiency (0.277 / 0.478 against 0.279 / 0.500 by meshblock).
  • An untracked read-only array type in the extension. share_lanes! uses CUDA.jl's public enable_synchronization!.
  • Lanes sharing written arrays. A cross-stream race on global memory is timing-dependent and invisible to the sanitizers; per-lane accumulator and child twins cost little memory.
  • Device-resident result arrays. A result type that depends on the resolved executor; the threaded host epilogues and caller storage of §2.7 take that host work.
  • GPUCompiler's disk cache, and deck-independent programs in the precompile workload. The disk cache keys only code instances that come from an image; with the preference set no file is written. A program's device code instance does not survive an image load, so a workload keeps only the compiler's native code, which the trivial program already warms.
  • Compile-ahead of a cold device cascade. No device cascade serves a Monte Carlo phase on a pool of CUDA devices.
  • Register caps on the scattering and crossing programs. Below the 5 % a cap must gain (§9).
  • The advance inlined into the kernel entry. On the A100 it runs the Compton phase in 0.843 of its time, bitwise; on a WaveHost the inlined Compton advance is not bitwise the package's, since host contraction follows the inlining context (I13). A change of an inlining boundary (class B), outside the standard until it passes the gates on both backends.
  • The site scan on a device, ports of the vendor library's functions, explicit-fma reductions in the physics, and host continuation of the slowest device rays. Each moves bits on a backend (class C) and waits for a re-baseline.
