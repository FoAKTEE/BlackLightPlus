Design principles

Status: adopted; test/structure.jl holds the gates of §5. Scope: the structure of src/, ext/ and test/. The physics, the numerical schemes and the validated results are inputs to this document, not its subject. The Repository standard governs the repository and its documentation.

Each principle is a rule, the evidence that motivates it, and a check a reviewer can mark pass or fail.

1. Goal

The current code is correct, validated and fast. Its structure makes four things expensive: finding where a concept lives, adding a combination of existing capabilities, loading the GPU path, and reading a driver end to end. The next generation keeps every physics function, numerical scheme and determinism contract, and reorganises them so that

  1. every concept has one definition in one module, and the module graph has one direction;
  2. a spacetime, a matter model, a transfer mode, a ray source, a backend and a precision lane combine by argument, never by a new function;
  3. the GPU path is ordinary package code: namespaced, precompiled, and run in CI on the KernelAbstractions CPU backend;
  4. a driver reads as a short pipeline.

Non-goals: new physics; changing the reverse-accumulation transfer scheme, the march termination rule or the fp64 default; any kernel register, stack or spill growth beyond the bench/kernel_audit.jl tolerance.

2. What is preserved

These are design decisions of the current code that the next generation keeps verbatim. They are the reason the rewrite is a reorganisation and not a reimplementation.

  • The hot-path rule. Everything reachable from a march is pure, allocation-free, isbits and StaticArrays-typed, so one implementation serves CPU threads, KernelAbstractions kernels and ForwardDiff/Enzyme (CONTRIBUTING.md, Repository standard §9).
  • One physics source. The metric methods and AD-derived derivatives (geodesics/metrics.jl), the plasma decode and synchrotron fits (radiation/coefficients.jl), the tetrads, the segment operators (radiation/transfer.jl) and the two reverse marches (radiation/reverse_march.jl) are called by the CPU drivers and compiled in-kernel by every GPU driver.
  • The march abstraction. reverse_unpolarized_march and reverse_polarized_march, parameterised by a march control (KerrMarch, SpacetimeMarch, StoredPath) and a sampler, with one termination rule (march_stop).
  • Spacetime as a type. metric, inverse_metric, raise_and_norm, lower_index, spacetime_control dispatch on the spacetime; a new metric defines metric(st, x) and inherits the engine. The ADM grid's device twin (DevADMParams) runs the CPU bodies by duck typing.
  • Determinism. Per-item outputs independent of chunking and device count; exact integer-limb accumulation for every reduction (montecarlo/exact_sum.jl); Monte Carlo streams keyed by genealogy (montecarlo/rng.jl).
  • The device pool and the per-item executor (gpu_pool.jl: DevicePool, march!, MarchPart, CameraRays, resident).
  • The two-phase stored-trajectory path (trace_rays_sampled + StoredPath) as the validation and adaptive-tracer route.
  • The test culture: analytic solutions, cross-code references, bitwise device-invariance decks, the offline kernel audit.
  • Repository standard in full except the two rules in §6.

3. Principles

A. Structure

P1. Layered, one-directional module graph. Rule. The package is a stack of layers; a module imports only from layers below it. The layers, bottom up: Core (numeric utilities: exact sums, counter-based RNG, interpolation stencils, physical constants, units), Spacetime (metrics, geodesic engine, cameras, the exact-Kerr tracer and its orbit primitives), Matter (the plasma-state protocol and its providers: AthenaK snapshots, snapshot series, analytic sources, emission zones), Transfer (coefficients, tetrads, segment operators, the imaging marches, the Monte Carlo transport), Execution (executors: native threads, the KernelAbstractions device pool; residency; ray sources), Drivers (run preparation and the product entry points), Analysis (image-plane refinement indicators, interferometry, writers). No file at root scope composes modules. Why. D9. Back edges are today resolved by callbacks (equatorial_intensity's source), re-exports and root-scope files. Check. test/structure.jl, "layering": every using ..X or import ..X of a module names a module before it in Numerics, Spacetime, Matter, Transfer, MonteCarlo, Data, Execution, Plans, Analysis, Products; no physics module imports KernelAbstractions, HDF5, CUDA or Base.Threads; no physics or pipeline file contains Threads.@threads.

P2. One package; optional backends are extensions. Rule. All kernels, the device pool and the executors are package code written against KernelAbstractions, which is already a hard dependency. Code that needs CUDA (device activation, pinned host memory, NVML probing, stack limits, unsafe_free!) lives in ext/BlackLightPlusCUDAExt.jl; CUDA and Enzyme move to [weakdeps]/[extras]. There are no include guards and no include-order contract anywhere in src/, test/, bench/ or figures/. Why. D1, D2. The kernels already run on the KA CPU backend (HostDevice), which is how the device tests run without a GPU; nothing but the CUDA-specific glue requires CUDA at load time. Check. structure.jl, "one kernel, no device files, no include guards, no CUDA in src": no isdefined(@__MODULE__ and no gpu_*.jl file in src, no using CUDA/import CUDA and no CUDA. call there, and ext loads CUDA; the device tests run on HostDevices.

P3. Declared interfaces; private stays private. Rule. Each module declares its interface by export. Another module may use only exported names. A _-prefixed name is never referenced outside its module. What the top-level package exports is the public API (P16); what a submodule exports is an internal interface, documented, stable within a minor version, and the only thing tests may import from it. Why. D3. Check. structure.jl, "private names stay private": no Module._name between the ten modules and no using ..X: _name in src, no BlackLightPlus.X._name in test or test/oracle; "eponymous files own includes and exports": a module's include( and export lines are in its eponymous file only; "public API": every name a submodule exports is defined and has a docstring.

B. Composition

P4. Axes are arguments, never names. Rule. The imaging axes are: spacetime (a Spacetime value), matter (a PlasmaProvider value, P5), transfer mode (StokesI() or IQUV()), ray source (camera frame, coordinate list, refinement block), executor (P8), lanes (P7) and time dependence (a property of the provider). There is one image entry point and one spectrum entry point per product; a new combination of existing axes requires no new function and no new kernel. Kernels exist only for genuinely distinct per-item programs: the two transfer marches, the trajectory tracer, the shadow tracer, the analytic tracer, the Monte Carlo primary and layer kernels, the camera-ray kernel. The sampler and the spacetime enter a kernel as arguments. Why. D4, D5. The current marches already take the sampler and the control as arguments; the drivers and kernels do not. Check. structure.jl: exactly one @kernel in src ("one kernel, …"); at most 10 exported names in the render/trace/shadow/mc_spectrum/ sensitivity/variants/photon_ring_layers family ("public API").

P5. One matter protocol. Rule. A PlasmaProvider answers plasma(provider, x) for a four-position x with one typed record: the code-unit primitives (rho, uu, eint, bb) and a validity flag, or nothing-equivalent vacuum with a single representation. Snapshots, snapshot series (time blending), analytic sources and the Monte Carlo zone list are providers; the cgs decode (plasma_decode) is applied by the transfer layer, once. A provider's device twin is the same struct with device arrays (Adapt.@adapt_structure), sampling through the same body. One trilinear interpolant, one time blend, one vacuum sentinel. Why. D7, D8. DevADMParams already proves the pattern for spacetimes. Check. structure.jl, "one concept, one home": the trilinear blend (c100 - c000) in one file and one vacuum definition in src; no "keep in sync", "twin of", "byte-for-byte" or "ported from" there.

P6. Prepare once. Rule. RunConfig is declarative user input. prepare(cfg; spacetime, matter, …) returns an immutable plan that owns everything derived: the spacetime, the camera and its frame, the horizon and escape radii, the emission-confinement radius, the units, the frequency, the transfer parameters with their precomputed nonthermal constants, and the lanes. Drivers, kernels and executors consume the plan. No derived scalar is computed in a driver. Why. D5, D6. Check. structure.jl, "one concept, one home": 1 + sqrt(1 - a only in kerr_schild.jl, kerr_orbits.jl and analytic_kerr.jl, and no sqrt(1 - a in src/pipeline; 1.1 * in the pipeline only in config.jl; at most one PlaneParallelCamera( in the pipeline.

P7. Typed parameter records and explicit lanes. Rule. The march parameter set is an immutable, documented struct TransferParams{T} (units, electron model, cuts, frequency, length unit, camera vertical) with the nonthermal populations as optional typed sub-records (Nothing when absent, so selection is at compile time, as hasfield is today). SimCoeffConfig and coefficient_params disappear; the host precompute returns the record instead of mutating one. The AD lane is TransferParams{Dual}; the K-variant ladder is an NTuple{K} of records. The geodesic lane type and the transfer lane type are set once in the plan (Lanes{Tg,Tt}) and flow by dispatch; no driver converts scalars by hand. Bool fields are Bool. Why. D6, D12. Check. No NamedTuple crosses a kernel boundary as a parameter set; no Float32( call in a driver; one definition of the lane rule.

P8. One executor per backend; the backend is a switch; a driver is a pipeline. Rule. An executor runs a per-item function over an index set and writes per-item outputs: ThreadedExecutor (native threads, host arrays) and PoolExecutor (the device pool over KA backends, CPU or CUDA). Reductions go through exact accumulators merged in item order. Where a product runs is one keyword, backend, accepted by every product, with a session default (backend!) and an environment override (BLP_BACKEND); a plan never records a backend; :auto logs its choice once, and an explicit choice that cannot be honoured is an error, never a silent downgrade. Every driver has the same shape: resolve backend → ray source → march under executor → assemble product. The Monte Carlo drivers follow the same shape with generate/track/record as the per-item function. Why. D13, D4. march! and MarchPart are the executor for one backend already; the CPU side hand-rolls 23 loops; today the backend is chosen by calling a differently named function after a differently ordered set of includes. Check. structure.jl, "threads only in the executor and the Data loaders and builders": the files with Threads.@threads are infra/Execution/executor.jl and files under infra/Data/, at most five; "layering": none in physics or pipeline. Every product accepts backend (test/pipeline/products_backend.jl).

C. Readability

P9. One concept, one name, one home. Rule. Each concept is defined once, in the module that owns it, under one name: horizon radius, escape radius, vacuum, the trilinear stencil, the Stokes-plane reshape, the camera vertical, the Kerr orbit radii. Modules replace prefix pseudo-namespaces. Re-exports are allowed only upward through the layer stack, never sideways. Why. D5, D8, D9; the Kerr orbit primitives are exported by Geodesics, re-exported by Radiation and Sources. Check. structure.jl, "one concept, one home": the greps of P5, P6 and P10.

P10. Records over positional tuples; accessors over indices. Rule. A value with three or more fields crossing a function boundary is a NamedTuple with documented field names or a small struct, never a positional tuple. The eight-component ray state has position(y), momentum(y) and a constructor; callers never index y[5]. Multi-flag results (stop, h, r) are named. Why. D10. Check. structure.jl, "one concept, one home": the SVector(y[1], y[2], y[3], y[4]) pattern appears only in Numerics/raystate.jl.

P11. Comments carry contracts; documents carry derivations. Rule. A docstring states the contract: inputs, units, conventions, outputs, failure behaviour, and one reference. A comment states an invariant or a non-obvious reason. Heritage ("after blacklight X.cpp"), deviations from reference codes, measured errors and history live in docs/src/method.md, NOTICE and CHANGELOG.md, and the code points to them by section. A file head is at most ten lines: role, layer, counterpart, reference. Why. D11; STANDARDS §3 "one fact, one home". Check. structure.jl: no "keep in sync", "twin of", "byte-for-byte" or "ported from" in src ("one concept, one home"), and no attribution line in src, ext, test, README.md or Project.toml ("no attribution or process prose").

P12. Size and arity budgets. Rule. A function takes at most six positional arguments; beyond that the arguments are a record. A file is at most ~500 lines and one concern. A kernel body is one call to a march plus the output write. A product entry point is at most ~40 lines. Why. D10, D4; _mc_grmhd_loop! takes 20 positional arguments, gpu_image.jl and gpu_amr.jl each mix four concerns. Check. structure.jl, "file budgets": every file of src is at most 600 lines, and no stray test_*.jl file sits in test.

D. Contracts

P13. The hot-path rule, enforced. Rule. Unchanged from today (§2), now tested: each march is compiled with a Float64, a Float32 geodesic lane and a Dual transfer lane on the KA CPU backend, and @allocated of one march call is zero; the offline kernel audit runs in CI against its baseline. Check. The test exists and passes; the audit gate is a CI step.

P14. Determinism per entry point. Rule. Every product entry point states its determinism contract in its docstring, one of: bitwise per item (independent of executor, chunking, device count and queue order), bitwise reduction (exact accumulators merged in canonical order), or tolerance (with the tolerance and the reference). The existing device-invariance decks become the tests of these contracts. Why. The contracts exist today but are stated in prose in method.md and in scattered comments. Check. Each entry point's docstring has a "Determinism" line; a test references each.

P15. Continuity during the migration. Rule. The migration proceeds module by module with the suite green at every step. Where the arithmetic order is unchanged the output stays bitwise identical to the current code on the regression decks; where a unification changes arithmetic (the uniform-grid interpolant, the sampler layout) the change is accepted by physics tolerance against the CPU reference, documented in the changelog, and the pinned outputs are re-baselined once. No kernel's registers, stack or spill may grow beyond the audit tolerance. Why. results/blp/multigpu/design.md §5.6 set this policy for the previous consolidation; it worked. Check. Each migration commit cites the deck set it was checked against and states "bitwise" or the tolerance.

E. Surface, state, tests

P16. A small, product-shaped public API. Rule. The top-level package exports: the configuration types, the spacetime types, the plasma providers and sources, the transfer modes, the executors and device selection, the product entry points (render, render_amr, render_analytic, photon_ring_layers, mc_spectrum), the result types, and the analysis and writer functions: 54 names, the gate's ceiling. Everything else is a submodule interface (P3). Semantic versioning applies to the public API. Why. D14. Check. structure.jl, "public API": names(BlackLightPlus) holds at most 54 names, each defined, at most 10 of them in the product family of P4; every name a submodule exports is defined and documented.

P17. Global state confined to the execution layer. Rule. Mutable global state exists only in Execution: the pool registry, device residency, staging buffers. It is keyed by value where a value exists (a configuration key) and by identity with a weak reference otherwise, has a documented lifetime, and is behind one lock discipline. Physics and driver modules hold no caches; what they memoise (the critical curve, the cost order, leaf tables) is computed in prepare and stored in the plan or the provider. Why. D15. Check. grep -rn "const _[A-Z_]* = Ref\|ReentrantLock()\|Threads.Atomic" src hits only the execution module and provider constructors.

P18. Tests exercise contracts through declared interfaces. Rule. test/runtests.jl includes every test file unconditionally; a test skips, and reports the skip, only on a missing external resource (device, data file). Tests import public names or submodule exports, never _ names. Each principle's Check above that is mechanical (P1, P3, P6, P9, P10, P12, P16, P17) is a test in test/structure.jl, so the structure cannot regress silently. Why. D3, D14. Check. test/runtests.jl includes structure.jl and every file under physics/, infra/ and pipeline/ without condition; structure.jl keeps leading-underscore names out of test and test/oracle and stray test_*.jl files out of test.
