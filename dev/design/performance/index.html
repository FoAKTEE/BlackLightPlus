Performance

How BlackLightPlus spends its time, the knobs that change it, and every speed capability of the reference package (src/) with its form in BlackLightPlus. Protocols and types are specified in Architecture §4.2 and §5; the measurements are in Verification record §4 (CPU against the A100) and §4.1 (against the reference package on the same decks). The results of every product are bitwise independent of everything in this document: the executor, the chunk, the lane count, the device count, the queue order, the child-buffer capacity and the settings of the device wavefront change the wall time and nothing else.

1. Execution model

  • Programs and the one kernel. A product is a per-item program run by an executor: ThreadedExecutor calls it from Julia threads on the host arrays; PoolExecutor runs its device twin through the single _foreach! kernel on the lanes of a DevicePool. The program supplies its launch traits: workgroupsize (64 for the polarized imaging program, 32 for the Monte Carlo primary and layer programs, 128 for the stage and key programs of the device wavefront, else the backend's choice), stack_bytes (32 KiB for the exact-Kerr program), chunk_hint (an upper bound on its chunk under :auto) and register_cap (168 for the thin Monte Carlo primary, else the compiler's limit).
  • Threads. The items are cut into chunks in queue order; one worker task per thread pulls the next chunk from one queue (run_workers!), so the long marches at the head of a cost-ordered queue are spread over every thread and no thread idles on a contiguous run. A program's exception is rethrown as a CapturedException once the queue drains.
  • Pool. lanes persistent worker tasks per device (two by default), each with its own stream and pinned staging buffers, pull chunks from one shared queue. A chunk is one launch: a range of items goes to the kernel as it is (no index upload); any other item list is staged as Int32 when it fits, Int otherwise. The outputs come back through the lane's pinned staging and are scattered into the host arrays while the other lanes compute. The launches of the lanes of a device overlap: they share the residency arrays, which they only read (share_lanes!), and own every array they write; every pool job ends with sync_lanes. The first failure is rethrown after the queue drains.
  • Residency. Every host array a program holds is uploaded once per device and found again by identity (weakly held); the registry pool of a device list and lane count is shared by every executor built on it, whatever its chunk, so a change of chunk re-uploads nothing. backend = :gpu resolves to that pool. A product that overwrites host arrays a caller gives it (into) drops their device copies first (invalidate!).
  • Outputs in the product's layout. Programs write their final arrays: a Stokes I image is the output vector reshaped, the fifteen exact-Kerr maps are the fifteen output vectors reshaped (the analytic program visits the pixels in index order, so every chunk writes a contiguous run of each map). The host epilogues (the band sums, the NaN and zero maps, the split of the IQUV planes) run as programs (BandSum, Fill, Split) on Julia threads whatever the executor, and a product given into, an earlier result, writes its maps into that result's arrays instead of new ones. The AMR worklist paints block values in the visits.
  • Accumulators. Monte Carlo bins, the weight ledger and the scalar diagnostics are exact integer-limb sums (ExactBins, ExactScalars) written through atomics; each lane that runs a program writes its own zeroed twin, and gather! folds every lane's twin into the host sums.
  • Tables on the run's executor. The Monte Carlo zone tables (the weight table, every zone's count and envelope) and the hot-cross table are built where the run executes: on threads by the host builders of Data, on a pool by device programs (ZoneSums, ZoneCounts, HotcrossSigma) with the same arithmetic. Their logarithms and exponentials are tang_log and tang_exp, Base's table-driven algorithms written with explicit fused multiply-adds, which a device computes to the host's bits (the vendor library's exp and log differ in the last bit), the node coordinates and the Jüttner normalisations come from the host, and the per-node sums are exact limb sums, so the tables are bitwise the same on every executor. The zones and tables of the last grid run are kept for the next run on the same blocks, spacetime, parameters, zone options and generation settings.
  • The cascade. On threads, on host pools and wherever the wavefront does not serve, scattering runs as a cascade (foreach_cascade!): a chunk of primaries and every scattering generation of their children run on the worker that took the chunk. On a lane the children live in two device buffers swapped per generation, and the only host read per generation is their count; a generation records into lane scratch sums that are folded into the device's totals once its children fit, and a generation whose children overflow the buffer runs again in full after the buffer grows to the counted children and an eighth more, a rerun describe counts. A device generation starts with the larger of 4096 slots, half the chunk, the most children a generation on the device has spawned in the process, and the slots an eighth of the device's free memory holds (at most 16 per primary). On threads each task keeps two growing buffers and reruns only the photon whose children overflowed. Child streams are keyed by genealogy and the sums are exact, so the spectrum does not depend on the chunking, the lane or the arrival order.
  • The device wavefront. On a pool of CUDA devices a stationary Monte Carlo phase, thin or scattering, runs as the device wavefront (foreach_wavefront!, GPU execution §4): each device keeps a cohort of live photons on its first lane, advances every one by at most K loop iterations per launch (32 thin, 16 with children), retires the stopped ones, opens their children into the same cohort and refills it from a block counter the devices share, so a warp holds photons for K steps rather than a whole life (lane efficiency 0.98 at K = 32 against 0.19 for whole lives, Compton primaries). The scattering cohort is sorted by generation, then photon_key, before every advance; the launches of an iteration are queued without waiting, and the host waits only for the counter reads. The bins, the ledger and the child count are those of the cascade, bit for bit. A run over an emission window stays on threads.

The :auto chunk rule (chunk_for), applied per run from the item count n, the bytes of output per item and the program's chunk_hint:

  • a pool on one device: 2^20, one launch per run of up to 2^20 items;
  • a pool on d > 1 devices with l lanes each: clamp(cld(n, 2 l d), 2^16, 2^20), two chunks per lane where the run is large enough;
  • on a pool, at most max(2^16, 2^24 ÷ bytes), so one launch's outputs (16 MiB at most) are copied back and scattered while the other lanes compute;
  • threads: clamp(cld(n, 16 t), 16, 4096) on t Julia threads;
  • then at most the program's chunk_hint; an explicit chunk is used as given.

The cascade chunk (cascade_chunk): on a pool min(cld(n, 4 d), 2^20), a quarter of a device's share of the primaries, at least the executor's chunk when that is explicit; on threads cld(n, 64 t), at least the executor's chunk when that is explicit. An AMR worklist chunk holds max(1, c ÷ block²) blocks of c items.

What to tune, in order. The chunk only when a leg is known to prefer another size (bench/bench.jl with BLP_TUNE=1 sweeps lanes and chunks and records the best per leg); the lane count for kernels at the register cap; the queue for a movie; capacity only to avoid the overflow rerun on a deck whose scattering multiplicity is known. The wavefront's settings are the best medians of sweeps on the A100 (GPU execution §4.3) and change only for measurements.

Kernel resources. bench/kernel_audit.jl compiles the device twin of every program kind for sm80 without a GPU and reports registers, stack and spills against `kernelaudit_baseline.json;–checkfails on growth,–writerecords a deliberate change,–devicecompares with a GPU's own compilation (bench/README.md`).

4. Not carried, and why

  • The two-phase stored-trajectory render as the CPU default. BlackLightPlus's fused march is 1.2–4.3× faster on the CPU (Verification record §4.1); the stored path remains as render(plan, trajectories) on the host.
  • The GPU two-phase pipeline. Bound by the PCIe copy of the trajectories; the fused march on the device is faster on every leg.
  • Twenty-one specialised kernels. One kernel specialised on the program type compiles to the same device code per program; the audit lists forty-one such specialisations.
  • The separate camera-ray kernel. Replaced by the non-inlined camera_state inside the program. A two-launch form (a ray program writing Float64 rays into a lane buffer, then the march reading them by chunk position) is bitwise equal to the fused march but not faster on any program kind on the A100, and leaves the register counts of the Float32 lane (226) and of the IQUV programs (255) unchanged; rays stored already narrowed to Float32 change the Stokes I image of that lane. The register footprint of those programs is a question for the kernel audit, not for the camera ray.
  • The Compton sampler behind a non-inlined call. On the A100 the scattering kernel is slower with the boundary (743 ms against 643 ms in the scattering-sphere leg) and stays at the 255-register cap; on the CPU the boundary changes the last bits of the torus scattering spectrum against the reference, which the oracle compares exactly.
  • Diagnostic kernels (stiffness telemetry, sampler probes, render_with_powerlaw): measurements, not products; bench/ and the kernel audit take their place.
  • The level-synchronous adaptive closure. The streaming worklist queues a child as soon as its parent's visit returns; the level barrier only added launches.
  • The upload_bounds switch. Residency uploads every array a program holds once; there is nothing to switch.
  • The lazy leaf-table build. The table is built with the blocks in Data, once.
  • The single-device default for the exact-Kerr product. The product runs on the resolved executor like every other; its maps are written per chunk, so several devices share the work without a host epilogue.
  • Device-side trajectory logs for trace. The tracer resumes exactly from 20-step windows; a ragged per-item column output in Execution would replace the relaunches (at most 125 for a 2,500-step march) and is the one remaining item of the record.

The site scan, whose code is the same on both trees, measured 1.07 and 1.18 of the reference in the first and second call of the CPU timing processes and 1.018 [0.784, 1.139] in a series of six pairs of nine calls.
