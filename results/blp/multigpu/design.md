# Multi-GPU efficiency of BlackLightPlus: design

Scope: multi-GPU efficiency of the fused imaging kernels, the adaptive (AMR)
image driver and the GPU Monte Carlo (MC). The criteria, in priority order:
correctness, accuracy, speed, code quality. The node DAG that implements this
design is in `dag.md` (nodes `MG01`–`MG15`). Every code reference is to
branch `paper` at `3736b32`.

## 0. Evidence base and conventions

- **No GPU is usable on the host** (NVML error; `CUDA.functional() == false`),
  so no kernel was timed. The evidence types are listed below.
  1. *Published*: the benchmark numbers in `docs/src/benchmarks.md`. They
     were taken on 2× A100 80 GB with 2× Xeon Platinum 8360Y, which is the
     host these nodes run on.
  2. *Measured here* (CPU, single thread, `julia 1.12.6`). These are the
     costs of the host work that runs serially inside timed GPU calls.
  3. *Offline compile audit*: PTX generated by GPUCompiler for `sm_80`
     without a device, then `ptxas -arch=sm_80 -v`. This gives register,
     stack and spill counts per kernel (§0.2).
  4. *Code reading*, with `file:line` references.
- **Amdahl convention.** Split the single-GPU time into a non-parallel part
  and a parallel part, T₁ = s + p. Then the n-GPU time is Tₙ = s + p/n, and
  the non-parallel fraction f = s/T₁ gives S₂ = 2/(1+f). A measured S₂
  implies f = 2/S₂ − 1. The published scaling therefore implies the
  following fractions:

  | path | published S₂ | implied f |
  |---|---|---|
  | full frame, fused | 1.74–1.82× | 0.099–0.149 |
  | through the AMR driver | 1.64–1.67× | 0.198–0.220 |
  | production AMR image | 1.645× (2.78 s → 1.69 s) | 0.216, i.e. s = 2T₂ − T₁ = **0.60 s** |
  | MC | 1.81× (thin) / 1.73× (scatter) | 0.105 / 0.156 |

  The targets translate into these ceilings on f:
  - S₂ ≥ 1.90 requires f ≤ 0.053.
  - S₂ ≥ 1.85 requires f ≤ 0.081.
- **Risk tiers.** The repository defines no R0–R4 rubric
  (`code-quality-intake`), so this design uses its own:
  - **R0**: read-only tooling.
  - **R1**: harness or docs, with no change to production outputs.
  - **R2**: a performance change whose outputs stay bitwise-identical to the
    pre-change code.
  - **R3**: concurrency changes, or changes to pinned numerical outputs
    (these need re-baselining with a delta report).
  - **R4**: a public API break or data loss. No R4 node exists: every
    `render_gpu_*`, `march_rays_gpu_*` and `mc_spectrum_gpu` signature stays
    callable.

### 0.2 Offline kernel resource audit (sm_80, f64 unless noted)

Default KernelAbstractions (KA) config, `always_inline = false`:

| kernel | registers | stack frame | spill stores / loads |
|---|---|---|---|
| `_fused_kernel!` (uniform grid, Stokes I) | 242 | 2208 B | 0 / 0 |
| `_famr_kernel!` (native AMR, Stokes I) | 254 | 2208 B | 0 / 0 |
| `_gpol_kernel!` (uniform grid, IQUV) | 255 (cap) | 3296 B | 792 B / 880 B |
| `_gpol_amr_kernel!` (native AMR, IQUV) | 255 (cap) | 3304 B | 784 B / 872 B |
| `_gpol_amr_kernel!`, fp32 geodesic lane | 255 (cap) | 2152 B | 620 B / 756 B |

A register count of 242–255 allows at most 256 resident threads per SM (8 of
64 warps). **One resident wave is therefore 108 × 256 = 27,648 rays per
A100.** Any batch smaller than about 2 waves per device (≈55k rays) cannot
hide latency. The stack frames of 2.2–3.3 KB are local-memory traffic.

The recipe works without a GPU:

1. Build `GPUCompiler.PTXCompilerTarget(cap=v"8.0", ptx=v"7.8")` and
   `CUDA.CUDACore.CUDACompilerParams(sm=SMVersion(v"8.0"), ptx=v"7.8")`.
2. Take the method instance of the KA kernel's `obj.f` with argument types
   `(KA.mkcontext(...), CuDeviceArray{…,AS.Global}…)`.
3. Run `GPUCompiler.compile(:asm, job)`.
4. Run `ptxas -arch=sm_80 -v` from the CUDA artifact.

Node `MG02` turns this into a regression guard.

### 0.3 Timing model fitted to the published single-GPU throughput

Single A100, fused unpolarized kernel, same deck:

| resolution | throughput | T₁ |
|---|---|---|
| 192² | 3.9×10⁵ rays/s | 94.5 ms |
| 384² | 5.9×10⁵ rays/s | 250 ms |
| 768² | 6.3×10⁵ rays/s | 936 ms |

A linear fit T(N) = a + N·c through the 384² and 768² points gives:

- a ≈ **21 ms fixed per call** (launch, synchronisation, the device probe,
  and the latency of the longest ray);
- c ≈ 1.55 µs/ray.

The measured host work (camera rays plus gather) accounts for h ≈ 0.17 µs of
c, which leaves g ≈ 1.39 µs/ray of GPU work. At 192² the model under-predicts
by 16 ms. That is wave quantisation: 36,864 rays is 1.3 waves.

For n GPUs the model gives T_n = a + N·(h + g/n). At 768² this predicts
S₂ = 1.78, inside the published 1.74–1.82×. With x = a + N·h the
non-parallel time:

| target at 768² | condition |
|---|---|
| S₂ ≥ 1.90 | x ≤ 45 ms |
| S₂ ≥ 1.85 | x ≤ 90 ms |

At 384² the 1.90× target requires x ≤ 11 ms.

Today x ≈ 21 + 98 = 119 ms at 768². This model is an estimate. Node `MG01`
replaces it with phase-resolved measurements.

## 1. Current multi-GPU architecture (as built)

### 1.1 Work split

| path | split | reference |
|---|---|---|
| fused unpolarized / polarized / native-AMR / slow-light / K-variant / AD / generic-spacetime imaging | static **interleaved** split: device `di` gets `pool[di:nd:end]` | `gpu_image.jl:557-569`, `gpu_pol.jl:730-742`, `gpu_amr.jl:278-302`, `gpu_spacetime.jl:487-513`, `gpu_image_ad.jl:100-108` |
| two-phase tracer `trace_rays_gpu` | static **contiguous** halves | `geodesics/gpu_tracer.jl:199-209` |
| analytic kernel | static contiguous split | `gpu_analytic.jl:94` |
| MC (thin and scatter) | static equal photon counts; per-device seed = seed + (di−1)·2³⁰ | `montecarlo/mc_gpu.jl:236-268`, `549-579` |

- The interleaved split balances the *distribution* of ray costs across
  devices: photon-ring grazers, captured rays and cheap escapes each land
  about half on each device.
- The split does **not** balance the *latency* of the longest rays or the
  granularity of the last wave. It cannot react to a slower or shared
  device, because there is no dynamic work queue anywhere.
- `order = march_sort_order(counts)` sorts rays by **ascending** trip count
  (`gpu_image.jl:457`). Blocks are dispatched roughly in index order, so
  this puts the longest rays in the final wave, which is the worst case for
  makespan.

### 1.2 Host orchestration

Every multi-device call is the same block, repeated 18 times across `src/`:

```julia
@sync for di in 1:nd
    ...
    @async begin
        CUDA.device!(dev)
        ...
    end
end
```

- `@async` tasks run on the **calling OS thread**. CUDA.jl's `synchronize`
  yields to other tasks, so kernels on different devices overlap. All host
  work inside the tasks is serialised across devices, though:
  - the gather `rays[rng]`;
  - the pageable `CuArray(...)` upload;
  - the blocking pageable `Array(outd)` download;
  - `img[rng] .=`;
  - JIT compilation;
  - in the MC path, the host table builds.
- Each task uses CUDA.jl's task-local stream on its device. There is one
  launch per device per call, so upload, compute and download never overlap.
- Devices are chosen per call by the default argument
  `devices = select_devices()`. That function has three copies:
  `gpu_image.jl:394-429`, `gpu_tracer.jl:19-53` and `mc_gpu.jl:35-69`. It
  probes NVML and memory, and calls `CUDA.device!` on every candidate.

### 1.3 Transfers

- **Rays** are built on the host and uploaded per call, per device, from
  pageable memory: 64 B/ray, so 38 MB at 768² (`gpu_image.jl:543`).
- **Outputs** are downloaded pageable, then scattered (`gpu_image.jl:548`).
- **Pinned memory**: none is used anywhere in `src/`.
- **Fluid** data is resident only if the caller passes a pre-uploaded
  `DeviceFluidGrid` or `DeviceAMRGrid`.
  - Passing a `UniformFluidGrid` re-uploads it on every call. At n = 256 it
    is 8·256³·4 B = **537 MB per device per call**
    (`gpu_image.jl:635-638`).
  - Passing an `AthenaKSnapshot` re-resamples and re-uploads it on every
    call.
  - The same holds for `march_rays_gpu_amr` given a snapshot
    (`gpu_amr.jl:329-330`). An AMR driver closure written that way pays a
    full-snapshot upload per refinement level.
  - `docs/src/guide/gpu.md` shows exactly that pattern:
    `render_gpu_amr(cfg, snap)`.

### 1.4 Launch configuration

- The unpolarized kernels use the KA default workgroup size, which CUDA's
  occupancy API chooses. At 242–254 registers that is one 256-thread block
  per SM. **A block holds its SM until its slowest of 256 rays finishes**, so
  divergence costs at block granularity, not only warp granularity.
- The polarized kernels use `wg = 64` (`gpu_pol.jl:707-711`): 4 blocks per
  SM, which halves that granularity.
- The per-kernel resource usage is in §0.2.

### 1.5 AMR batching

The driver works level by level (`amr.jl:195-226`):

1. Build the coordinates on the host.
2. Call `stokes_at(coords)` for all blocks of the level: a full barrier on
   every device.
3. Run the refinement indicator and paint serially on the host.
4. Build the next level.

Late levels can be far below one wave per device. The i = 90 BBH deck, for
example, has level histogram [959, 1, 0, 0, 64] (`3736b32`). The host part
costs 0.40 µs/ray serially plus 0.11 µs/ray for camera rays (§0.1).

### 1.6 JIT

- Each kernel is compiled on first use per device context, inside the
  `@async` task, so compilation for the two devices is serial on one thread.
- The benchmarks exclude warm-up. First-call cost for the polarized AMR
  kernel is `NEEDS_EVIDENCE` (`MG01` measures it).
- The analytic kernel also raises `LIMIT_STACK_SIZE` per device on every
  call (`gpu_analytic.jl:105`).

### 1.7 MC RNG and reduction

- Primary photon `i` on device `di` uses the key
  `(seed + (di−1)·2³⁰ mod 2³², i)` with a 32-bit draw counter
  (`rng.jl:82-100`, `mc_gpu.jl:249-250,299`).
- A child photon's stream is `MCRng(child_seed, j)`, where `j` is its buffer
  slot taken with `CUDA.atomic_add!` (`mc_gpu.jl:409,474`).
- Spectrum bins and diagnostics are Float64 atomics
  (`mc_gpu.jl:199-201,387-389,449-451`).
- On the CPU, child keys depend on the chunk index, and the chunk count is
  the thread count (`mc_cpu.jl:161-172`).

### 1.8 Determinism of the imaging paths

- Every imaging kernel writes one independent output per ray, with no
  cross-ray reduction.
- Host reductions (the AD flux, the stiffness totals) run in a fixed order.
- Image results are therefore bitwise invariant under device count, split,
  `order` and `wg` **on identical GPU architectures, by construction**.
- No test exercises more than one partition or device (§2, C7).
- `select_devices` may pick GPUs of different architectures. Different SASS
  can then change fused multiply-add (fmuladd) contraction, so the images
  would differ at the ulp level.

### 1.9 Precision paths

- **`:f64`**, the default.
- **`:mixed`**: fp32 geodesic and frame lane, fp64 radiative transfer. It
  adds a second fp64 sweep over the pixels within `rescue_px` of the
  critical curve (`gpu_image.jl:658-667`, `gpu_pol.jl:794-803`,
  `gpu_amr.jl:409-417,474-482`).
- **`:f32_raw`**: diagnostic only.
- On A100, where FP64 runs at ½ the FP32 rate, the polarized fp32 lane still
  sits at the 255-register cap and spills (§0.2).
- The rescue sweep is a separate, small, fully synchronised launch made
  entirely of the most expensive rays. It is pure tail (finding F4).

Reading the table:

- **F1 alone reproduces the published full-frame ceiling.**
- **F1 + F3 explain the 768² vs 384² difference.**
- **F2 dominates the AMR driver.**

Reaching ≥1.9× at 768² needs F1 removed (rays generated on the device, work
queued) and F3 reduced below 45 ms of non-parallel time. Reaching ≥1.85×
through the AMR driver needs F2 removed (resident data, parallel host work,
no per-level barrier) together with F1 and F3.

## 3. Correctness and accuracy risks in the multi-GPU paths

Findings follow the `code-quality-review` schema. They are grouped by kind:
MC reproducibility (C1–C3, C10), consistency of the termination criteria
(C4–C6), and missing tests, device choice and copy drift (C7–C9, C11).

### MC reproducibility

**C1: HIGH, CONFIRMED (code reading).** MC scatter child streams are keyed
by an atomic buffer slot.

- In `mc_gpu.jl:409` a child's slot comes from `atomic_add!`, which follows
  thread timing.
- In `mc_gpu.jl:474` the child's random stream is `MCRng(child_seed, j)`,
  with `j` that slot.
- Which physical child receives which stream is therefore scheduling
  dependent. **Scatter spectra are not reproducible run to run, even on one
  GPU with a fixed seed.**
- The statistics stay valid, since every child gets a unique stream.
- `docs/src/benchmarks.md` claims bitwise GPU-CPU parity for MC replay of
  matched RNG streams. That holds only for the thin (no-scatter) kernel.
- Fix (`MG05`): key each child by (parent global id, event index) and draw
  counter, never by slot.

**C2: MEDIUM, CONFIRMED.** Streams depend on device count, and the seed
wraps.

- Device `di` uses `seed + (di−1)·2³⁰`, masked to 32 bits
  (`mc_gpu.jl:32,249,299`), with photon ids local to the device.
- Results therefore depend on the number of devices.
- Because 4·2³⁰ = 2³², **device 5 reuses device 1's key**. Its primaries
  replay device 1's exactly: correlated samples, with the variance
  underestimated.
- There is no domain separation between primary and child keys: both use
  the same `(key₁, key₂ = id)` layout (`rng.jl:88-89`).
- Fix (`MG05`): use a global photon id for every photon, and a
  domain-separated key word (primary / child / layer).

**C3: MEDIUM, CONFIRMED.** MC float atomics and the CPU chunking are not
deterministic.

- On the GPU, float atomics make the summation order scheduling dependent
  (roughly 1e-15 relative jitter).
- On the CPU, child keys depend on the chunk count, which is `nthreads`
  (`mc_cpu.jl:161-172`). CPU results depend on the thread count.
- Fix (`MG06`): exact two-level Int64 fixed-point binned accumulation on the
  CPU and the device. Integer addition is associative, so the result is
  bitwise independent of order, device count and thread count.

**C10: LOW-MEDIUM, CONFIRMED.** Scatter-buffer overflow drops children, and
which ones is timing dependent.

- Children past the buffer capacity are dropped (`mc_gpu.jl:411,680`). A
  warning is emitted.
- Which children are dropped depends on timing, so the bias is
  nondeterministic.
- Fix (`MG05`): with the pool, a child layer flushes in fixed-size chunks and
  never drops a child.

### Consistency of the termination criteria

**C4: MEDIUM, CONFIRMED (inconsistency); effect NEEDS_EVIDENCE.** The
frame-drift stop exists only in the polarized fused marches.

- The stop was added in `1e3707c`: it ends the march when |−k·e_Uu − w_cam|
  exceeds 1% of w_cam (`gpu_pol.jl:585-586,646`, `gpu_spacetime.jl:271`).
- The CPU `polarized_march` has no counterpart, and neither do the
  unpolarized GPU marches (`_gimg_stop`, `gpu_image.jl:324-325`).
- Consequences:
  - GPU polarized and CPU polarized integrate different near-horizon segment
    sets.
  - The GPU polarized I differs from the GPU unpolarized I on the same
    trajectory.
  - In `:mixed` the frame is transported in fp32, so the 1% gate may trip
    away from the horizon, for example on photon-ring rays with many steps.
    This is unverified.
- Fix (`MG04`): one shared termination policy used by the CPU tracer, the
  CPU marches and every kernel. Tests pin the emitting-segment set and bound
  the radius at which the drift stop fires.

**C5: LOW, CONFIRMED.** The horizon epsilon is duplicated as a literal.

- The capture epsilon appears as a literal `1e-3` in `gpu_image.jl:324-325`
  and `gpu_tracer.jl:82`.
- The source of truth is `HORIZON_EPS_SAMPLED` (`integrator.jl:17`).
- The two copies can drift apart silently. Fixed by `MG04`.

**C6: DISMISSED as a multi-GPU risk.** The superposed capture from `bb233b2`
is single-source.

- `_gsp_ctl` calls the CPU `superposed_control` (`gpu_spacetime.jl:80-81`),
  so the sampled CPU tracer and the fused generic kernels share the capture
  criterion, including `CAPTURE_REDSHIFT = 1e2`.
- The residual difference is C4: the polarized GPU march adds the drift stop
  on top.

### Missing tests, device choice and copy drift

**C7: MEDIUM, CONFIRMED.** Device-count invariance is untested.

- No test runs more than one partition or device. `test_slow_light.jl:190`
  uses `devs = [0]`, and the others use `devices = Int[]` for argument
  validation only.
- There are no tests of the MC GPU kernels.
- Imaging invariance holds by construction (§1.8) but is unverified.
- Fix (`MG03`): tests-first invariance suite on the KA CPU backend.

**C8: LOW, NEEDS_EVIDENCE.** A mixed-architecture device set would change
bits.

- `select_devices` does not require equal compute capability.
- Policy: warn, and document that a mixed-architecture device set gives only
  ulp-level agreement.

**C11: MEDIUM, CONFIRMED (drift pattern).** The device copies of the CPU
physics drift.

- `test_transfer.jl:169-171` records a past drift: `_gpol_thermal` lacked
  the CPU rho_Q blend.
- A live divergence: the CPU `eight_coefficients` rejects `b_sq == 0.0`
  (`radiation/integrator.jl:28`), while the device rejects `b_sq <= 0.0`
  (`gpu_image.jl:246`, `gpu_pol.jl:375`).
- The diagnostic stiffness kernel builds the transfer metric from the march
  spin `a` (`gpu_pol.jl:927`); production uses `gp.bh_a`
  (`gpu_pol.jl:632`).
- Fix (`MG12`): single source.

**Races.** The disjoint index writes into shared host vectors
(`img[rng] .=`) are race-free. They stay race-free under `Threads.@spawn`
only while outputs are plain `Vector`s written at disjoint indices. `BitArray`
is excluded; see the `render.jl:230-231` precedent.

## 4. Duplication and code quality

### 4.1 Inventory

- **Host orchestration.**
  - 18 copies of `@sync for di … @async … CUDA.device!`.
  - 19 `_part!` / `_sweep!` functions of the form: gather → upload → allocate
    → launch → synchronise → download → scatter.
  - 3 copies of `select_devices`.
  - About 12 copies of the driver prologue (camera, `gp`, `r_h`, escape,
    `R_em`).
  - 5 copies of the I/Q/U/V unpacking.
- **Kernels.** 20 `@kernel`s.
  - 13 imaging kernels are the product {Stokes I, IQUV} × {uniform, AMR
    leaf, AMR scan} × {fast, slow-light} plus the K-variant, stiffness and
    shadow variants.
  - Their bodies are already thin: a sampler closure passed to one march.
    The combinatorics are the duplication.
- **March bodies.**
  - `_gimg_march`, `_gimg_march_kv` and `_gsp_march` are three unpolarized
    marches.
  - `_gpol_march` and `_gsp_pol_march` are two polarized marches.
  - `_gpol_ext_rhs`, `_gpol_ext_rhs2` and `_gsp_ext_rhs2` are three
    transport RHSs.
- **Device copies of CPU physics**, justified by "fmuladd bit-exactness"

  `gpu_spacetime.jl:96-99`):

  | device copy | CPU original |

  | `_gimg_kappa` | kappa unpolarized coefficients |

  | `_gpol_powerlaw`, `_gpol_kappa` | `*_synchrotron_polarized` |

  | `_gimg_coeffs` and `_gimg_coeffs_st` | `eight_coefficients`' unpolarized branch |
  | `_gpol_coeffs` | `eight_coefficients` |
  | `_gimg_metric`, `_gimg_gi`, `_gimg_rhs` | `metric`, `inverse_metric`, `geodesic_rhs` |

- **Counter-evidence that a single source works.**
  - The generic-spacetime kernels already call the CPU `metric`,
    `rk4_step_fixed` and `superposed_control` in-kernel.
  - The MC kernels call the CPU `j_nu`, `alpha_nu` and
    `scatter_superphoton`.
  - The copies exist because `SimCoeffConfig` is a **mutable** struct
    (`coefficients.jl:91`) and cannot be passed to a kernel. The fmuladd
    argument protects regression *pins*, not physics accuracy: the CPU and
    GPU already agree only to ~1 ulp on the RHS (`gpu_tracer.jl:7-8`).

### 4.2 AHA checklist for the three proposed abstractions

| abstraction | ≥3 real sites | same decision | same reason to change | domain name | no mode flags | originals deleted | testable alone |
|---|---|---|---|---|---|---|---|
| `DevicePool` + `march!` executor (`MG07`) | PASS (19 `_part!`/`_sweep!` + 18 `@sync`) | PASS: "run a per-item kernel over an index set on devices, scatter per-item results" | PASS: device and transfer policy | PASS | PASS: the kernel and sampler are arguments, not flags | PASS: plan deletes all copies | PASS: KA CPU virtual devices |
| isbits coefficient parameters + single coefficient/tetrad functions (`MG12`) | PASS (CPU march, 3 unpolarized + 2 polarized device marches) | PASS: identical physics | PASS | PASS | PASS: eDF selection stays compile-time `hasfield` | PASS | PASS |
| sampler object replacing sampler closures (`MG13`) | PASS (uniform, AMR leaf, AMR scan, time blend) | PASS | PASS | PASS | PASS | PASS | PASS |

**Rejected: a single kernel serving both unpolarized and polarized modes.**
The two carry different state (1 vs 20 scalars), different registers and
different reasons to change. Fusing them would need a mode flag, which is the
AHA failure signal. The design keeps one march per radiative-transfer mode.

## 5. Target architecture

### 5.1 Device runtime (`MG07`)

- A `DevicePool` holds one persistent worker per device, spawned with
  `Threads.@spawn`. Julia must run with `-t ≥ nd+1`; the pool checks this
  and falls back to serial with a warning. Each worker owns:
  - its backend (`CUDABackend` on device d, or KA `CPU()` as a *virtual
    device* for tests);
  - two streams;
  - pinned host staging buffers;
  - a residency cache;
  - its compiled kernels, warmed concurrently at pool creation.
- **Residency.** `resident(pool, data)` uploads each fluid, AMR or metric
  object once per device, concurrently, from pinned staging, and returns a
  handle. The drivers accept handles; wrappers that are passed a snapshot
  upload once and cache by `objectid` for the pool's lifetime. This removes
  F5.
- **Work queue.** A global queue of fixed-size chunks, 32k–128k items
  (tuned in `MG14`).
  - Chunk boundaries depend only on the problem, never on the device count.
  - Workers pull chunks through an atomic counter.
  - Each chunk goes: upload the inputs, or none when rays are generated on
    the device (`MG08`) → launch → download the result into pinned memory →
    scatter to the global output index.
  - Double buffering overlaps chunk k+1's upload with chunk k's compute.
- **Single executor.** `march!(out, kernel_spec, items, pool; cost)` is the
  only multi-device loop in `src/`. It replaces the 19 `_part!`/`_sweep!`
  functions and the 18 `@sync` blocks. `select_devices` moves into the pool
  and is called once, when the pool is built, not per render.
- **Determinism.** Imaging outputs are per item, so any chunk-to-device
  assignment yields bitwise-identical images. The pool never reduces across
  items. Reductions (MC, fluxes) go through the exact accumulator of `MG06`
  and are merged in chunk-index order.

### 5.2 Ray generation on the device (`MG08`)

- The camera ray for a global pixel or coordinate index is computed
  in-kernel.
- It is the same `camera_rays_at` body, made isbits-callable (single source).
- Removes 82 ms at 768² of serial host time and 38 MB of upload.
- For the AMR driver the kernel takes block coordinates instead of pixel
  indices.

### 5.3 Cost-aware scheduling (`MG09`)

- Order chunks by descending predicted cost (longest-processing-time first)
  so the longest rays start first. Predictor inputs:
  - the image-plane distance to the Kerr critical curve (already computed
    for the rescue mask);
  - the parent level's trip counts (AMR);
  - the previous frame's trip counts (movies).
- Chunks are **tiles** (e.g. 16×16 pixels), not single rays, which keeps the
  fluid-sampling locality that `gpu_image.jl:452-455` warns about.
- `:mixed` rescue pixels enter the same queue as fp64 items at the front,
  with no second sweep. This removes F4.

### 5.4 AMR driver (`MG10`)

- Blocks are work items. A block's children are enqueued as soon as its
  result and indicator are available: no per-level barrier.
- The indicator and paint run in parallel threads on the host while the
  GPUs march.
- The final canvas is assembled deterministically in (level, block id)
  order, so the output is independent of completion order.
  - `render_amr` paints parents before children today; the ordered assembly
    preserves that overwrite semantics.
  - The level map uses `max`, which commutes.

### 5.5 Monte Carlo (`MG05`, `MG06`, `MG11`)

- **Keys.** `key = (seed, domain)`, where domain is primary, or child plus
  layer. The counter is (global photon id, parent event index, draw). Streams
  never depend on device, chunk, slot or thread.
- **Portable atomics.** KA-portable atomics (`Atomix`) let the MC kernels
  run on the KA CPU backend, which makes them testable without a GPU.
- **Exact accumulation.** A two-level Int64 fixed-point accumulator, where
  w = hi·2^e₁ + lo·2^e₂ with e₁ − e₂ = 31, and e₁ is set from a host bound on
  the maximum bin total. It is exact and associative (resolution about
  2⁻⁹³ of the bound), so it is bitwise invariant under order. Int64 atomics
  are native on the GPU. The overhead is measured in `MG06`/`MG11`.
- **Host tables** are built once per call and shared read-only across
  workers. This removes F6.

### 5.6 Single physics source (`MG12`, `MG13`)

- An immutable isbits `RTParams` replaces the ad-hoc `gp` NamedTuple and is
  built from `SimCoeffConfig`. Nonthermal fields stay optional, selected at
  compile time with `hasfield`.
- One set of coefficient, decoder, tetrad and Bessel functions serves both
  the CPU march and every kernel.
- The Kerr closed-form metric is a *method* of `metric` / `inverse_metric`
  on `KerrSchildCartesian`, not a copy.
- One unpolarized march covers Float64, Dual and `SVector{K}` accumulators,
  and one polarized march covers all polarized kernels. Both are
  parameterized by a spacetime object and an isbits sampler object.
- **Acceptance** is by physics tolerance against the CPU plus a one-time,
  documented re-baseline of the pinned regression outputs, not bitwise
  continuity. The speed guard is the offline audit: registers and spill
  bytes no higher than the `MG02` baseline for every kernel. The GPU
  throughput check (within −2%) runs when GPUs return.

## 6. What not to change

- **The fused per-ray reverse-accumulation scheme** (affine I and Mueller
  chain, transported readout frame). It is the source of the 11–19× gains
  and is validated against the CPU.
- **The two-phase stored-trajectory GPU tracer** (`trace_rays_gpu`). It is
  PCIe- and host-bound by design. It stays a validation tool with no
  optimisation effort (F7).
- **No splitting of a single ray across devices, no peer-to-peer or NCCL,
  and no in-kernel persistent-thread work stealing**, unless `MG09`
  measurements show residual intra-device tail above 3% of T₂. That change
  rewrites kernel bodies and risks the pinned-output contract for a gain
  that is not established.
- **`:mixed` numerics and the rescue-mask geometry.** Only the scheduling of
  the rescue pixels changes.
- **The analytic kernel's contiguous split.** Its per-pixel cost is nearly
  uniform. It moves onto the pool only when `MG07` deletes the duplicate
  loop, with its output kept bitwise-identical.
- **Public entry-point signatures and the include-not-import CUDA
  deployment**, including `devices=` keyword compatibility. The pool is
  additive (`pool=` keyword); `devices=` builds a transient pool.
- **fp64 as the default precision.**

## 7. Measurement protocol for every speed claim

All speed claims are made with the `MG01` harness, on the 2×A100 host with
exclusive GPUs. Each result is a warm best-of-5, with first-call (JIT) time
reported separately. Every leg emits `BENCH` and `PHASE` lines:
host-prologue, ray generation, upload, per-device kernel busy time
(CUDA events), download, host epilogue, and idle per device.

- **Baseline.** Captured on commit `3736b32` (pre-change) before any node
  claims a speedup. The `after` numbers come from the node's commit.
- **Scaling.** S₂ = T₁/T₂ on the same commit with `devices = [0]` vs
  `[0, 1]`. Invariance is checked in the same run: the 1- and 2-GPU outputs
  must be bitwise equal (`==` on the full arrays).
- **Legs.**
  - fused unpolarized 384², 768²;
  - fused polarized 256², 384²;
  - native-AMR Stokes I / IQUV at 384²;
  - AMR driver on the production deck (a = 0.9, 230 GHz, i = 60°, base 384,
    2 levels, polarized);
  - MC thin and scatter at Ns = 1e7.
- **Pass criteria.**
  - 768² full frame: S₂ ≥ 1.90.
  - 384²: report only, with target S₂ ≥ 1.85.
  - AMR driver end-to-end: S₂ ≥ 1.85.
  - MC thin: ≥ 1.90; MC scatter: ≥ 1.85.
  - Single-GPU throughput must not regress by more than 2% against the
    baseline for any leg.
